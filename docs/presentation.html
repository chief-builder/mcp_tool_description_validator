mcp-tool-validator · v0.1.0

MCP Tool Description Validator

A governance validator for Model Context Protocol tool definitions — catching the schema violations, security gaps, and ambiguous descriptions that make LLM agents misuse tools.

56 rules · 5 categories · CLI + HTTP API + library · live-server validation · optional LLM-assisted analysis

Why it exists

LLMs read descriptions, not code

An agent picks and calls a tool based purely on its name, description, and schema. Vague or contradictory definitions cause wrong tool choices, malformed arguments, and silent failures.

Schemas are attack surface

Unbounded strings, unconstrained numbers, and header-exposed secrets in tool schemas create injection and denial-of-service risks that ordinary code review rarely inspects.

The spec keeps moving

MCP has an official grammar for tool names, JSON Schema 2020-12 requirements, and a draft revision adding icons and x-mcp-header. Compliance is easy to drift from.

The validator turns all of this into a repeatable, CI-friendly quality gate with a single maturity score per server.

Maturity scoring

Each tool starts at 100. Deductions apply per issue — error −5, warning −2, suggestion −1 — and the server score is the average across tools, so one bad tool can't be hidden by fifty good ones.

Four ways to use it

1 · CLI

# files, live servers, CI gates
mcp-validate tools.json
mcp-validate --server "node ./my-server.js"
mcp-validate tools.json --format sarif --ci
mcp-validate tools.json --rule SEC-001=off

2 · Library

import { validate, validateFile,
  validateServer } from 'mcp-tool-validator';

const r = await validateFile('./tools.json');
r.valid; r.summary.maturityScore; r.issues;

3 · HTTP service

mcp-validate serve --port 8080
# GET  /health   → {status, version}
# POST /validate → full result
# bad config     → 400 with details

4 · Live MCP servers

# STDIO command or Streamable HTTP URL
mcp-validate -s "npx -y @mcp/server-memory"
mcp-validate -s "http://localhost:3000/mcp"

Exit codes: 0 success · 1 errors found with --ci · 2 input/usage failure. SARIF 2.1.0 output plugs into GitHub code scanning.

Configuration & precedence

# mcp-validate.config.yaml
rules:
  BP-001: off
  SEC-001: error
output:
  format: human
  verbose: false
specVersion: 2025-11-25   # or "draft"
llm:
  enabled: false
  provider: anthropic
  model: claude-haiku-4-5
  • Auto-discovered via cosmiconfig: mcp-validate.config.yaml/.yml/.json, .mcp-validaterc*, or a "mcp-validate" key in package.json.
  • Validated on load — unknown keys and invalid severities fail with a descriptive error, never silently ignored.
  • Precedence: defaults ← config file ← explicit CLI flags / HTTP overrides. Only flags you actually pass override file values.
  • HTTP parity — API request config goes through the same schema, so a bad override returns 400 with the exact field that failed.

Optional LLM-assisted analysis

Static rules catch structural problems. With --llm, each tool is additionally scored by a model for the things regexes can't judge:

Clarity score

Would an agent reading only this description know exactly what the tool does and returns?

Ambiguities & conflicts

Descriptions that contradict their own schema, overloaded parameters, undefined behavior.

Improvement suggestions

Concrete rewrites attached per tool in the result.

  • Providers are optional peer dependencies: @ai-sdk/anthropic, @ai-sdk/openai, or ollama-ai-provider-v2 — install only what you use.
  • Fail-safe by design: missing package, bad key, or network failure lands in metadata.llmAnalysisError; static findings always survive.
